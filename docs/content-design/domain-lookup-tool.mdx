# Domain Lookup Tool

<p className="hub-sub">If an Internet Threat Protection policy blocked or allowed a website unexpectedly, admins had no direct way to find the rule that caused it.</p>

<div className="ctx-prose">
  <p className="ctx-label">Background</p>
  <p>Internet Threat Protection is the part of Cloud Secure Edge that filters web traffic on company devices. For each website that a device requests, it checks for known threats. Then it applies the categories, apps, and websites that the organization blocks. Last, it applies the exceptions that the admin has set.</p>
  <p>When a website is blocked or allowed unexpectedly, the admin has to find the rule that decided the result. An employee is often waiting for access. I suggested a domain lookup tool inside the policy so that admins can check a website directly.</p>
</div>

## The problem

Before the tool, the only explanation was this diagram from the docs. It shows how Cloud Secure Edge routes a device's request to look up a website.

  </figcaption>

To diagnose a block, the admin has to apply their own configuration to one website. The diagram can't do that for them.

1. **Is the Service Tunnel on?** The Service Tunnel is the private connection to the company network. Whether a request uses it depends on the device and the admin's settings.
2. **Is the website on an exception list?** The admin has to check the include and exclude lists by hand.
3. **Which rule blocked it?** The web gateway applies the categories and rules that the admin set. The diagram doesn't show which one decided the result.

When an admin traces the answer by hand, the work is slow and errors are likely, especially while an employee waits.

## The approach

I proposed a lookup panel inside the policy itself, because the policy is where the admin is already working when a block happens. The panel opens with a note that states what the tool checks, and that it doesn't check blocks by country or by risk score. The admin reads this limit before running a lookup, so a clean result isn't mistaken for proof. Then the panel asks for one website address.

![The Lookup Domain panel. Callouts point to the note that states what the tool checks and what it doesn't, and to the field that asks for one website address.](/img/content-design/domain-lookup-tool-annotated.png)

The admin enters a website address in the policy. The tool shows whether the policy allows or blocks the website, and which category decided the result. The admin does not have to leave the policy to get the answer.

<div className="hl-after">

| | Before | After |
|---|---|---|
| **Where the admin looks** | A general diagram in the docs | A lookup panel inside the policy |
| **What the admin does** | Traces the diagram by hand, using what they remember of their settings | Enters one website address |
| **What the admin learns** | The paths a request could take | Whether this policy allows or blocks the website, and which category decided |
| **Limits** | Not stated | Stated up front: the tool doesn't check blocks by country or risk score |

</div>

## The constraint

<div className="ts-steps">

1. The tool does not check blocks by country or by risk score.
2. Without a warning, an admin could read a clean result as proof that the policy did not cause the block.

</div>

## The outcome

The team built the lookup panel into the Internet Threat Protection policy. Admins can now check a website in a few seconds, instead of tracing the docs diagram by hand. When an admin reports a block, support asks for the lookup result first, so many cases are settled before they're escalated.
