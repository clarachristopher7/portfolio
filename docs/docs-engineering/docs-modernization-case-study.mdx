# Documentation platform modernization

<p className="hub-sub">SonicWall's docs lived on two sites, and the docs team could change only one of them. Renaming a menu label meant filing a ticket with another team. I proposed one docs site that the docs team can actually change.</p>

<div className="ctx-prose">
  <p className="ctx-label">Background</p>
  <p>SonicWall makes firewalls, network management tools, and cloud security services. Most product docs lived on the main website, which the web team builds, so every navigation change meant a ticket to that team. The Cloud Secure Edge docs had their own site, which I run.</p>
  <p>I wrote a proposal for phase 1 of a modernization program, and built a working prototype to back it up.</p>
</div>

## The approach

I sorted the doc sets with one question. Do they ship with hardware, or carry a regulatory obligation? If not, why wait on a hardware release date?

For publishing, I chose Antora. It handles several live versions of one product (SonicOS needs that), and the docs team owns its navigation and templates. My prototype publishes four products from converted Flare content.

From the outside, nothing changes. Customers, search engines, and AI assistants still see one website. On the inside, the docs team publishes on its own schedule.

Some mistakes are too costly to prevent by being careful, so the worst three can't publish at all. An automated check stops the build if an old page address has no redirect, if a page shows the wrong firmware version, or if a certified doc changes.

## The constraint

The web team had six conditions. Fair enough. It's their website. The design had to meet every one.

| Condition | How the design meets it |
|---|---|
| **One website** | Docs are served at sonicwall.com/docs, with no separate docs domain. |
| **No loss of search ranking** | The hostname stays the same, and every changed page address redirects automatically. |
| **No disruption to site search, metadata, or AI answers** | Search tools still see one website. The pipeline writes page metadata from the source. |
| **One brand** | The docs use the web team's design tokens and stylesheet, so brand changes reach them on the next build. |
| **No added work for the web team** | The docs team runs its own pipeline. The web team adds one routing rule. |
| **No way for a writer to put the company at risk** | Automated checks block code in content. Only a lead writer can change navigation, and every change needs a recorded approval. |

## The outcome

The proposal went to the VP of Product in October 2026, with two questions. Should the docs team own the docs site? And should five doc sets move to docs-as-code publishing? The VP approved phase 1, and we're now building an internal preview of the new site.
