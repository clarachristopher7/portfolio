# Documentation impact evaluator

<p className="hub-sub">A scheduled job compares recent code changes with the docs. It reports the pages that the changes probably made wrong, and a writer decides what to change.</p>

<div className="ctx-prose">
  <p className="ctx-label">Background</p>
  <p>Engineers change the product every day. If a change affects a feature that a docs page describes, the page becomes wrong. Nothing in the release process tells the docs team.</p>
  <p>I designed and built a scheduled job to find those pages. Each run reads the latest code changes and checks which changes customers can use. Then Claude compares each change with an index of every docs page. The job writes a dated report of the pages that probably need an update.</p>
</div>

## How it works

<ol className="ia-steps ia-steps--4" aria-label="How the evaluator works">
  <li>Read recent code changes</li>
  <li className="is-new">Check which changes are live<small>Key step</small></li>
  <li>Compare each change with the docs</li>
  <li>Write a dated report</li>
</ol>

## Two lessons from building it

<HubGroup columns={2}>
  <HubCard icon="git" tag="Lesson" title="Read the code where new features arrive first">
    My first version read the copy of the code that the team uses for testing. It found one of the nine changes in a release. New features reach the main development code first, so the job reads that code now.
  </HubCard>
  <HubCard icon="search" tag="Lesson" title="A finished change is not always live">
    A change can be finished long before customers can use it. The job searches the code that the preview environment runs for distinctive text from each change. If the job finds the text, it marks the change as live.
  </HubCard>
</HubGroup>
