# Documentation impact evaluator

<p className="hub-sub">A scheduled job that compares recent changes to the product’s code with the documentation, and reports which pages those changes have likely made inaccurate. It is advisory by design: it flags pages, and a writer decides what to revise.</p>

<dl className="ctx">
  <div><dt>The situation</dt><dd>Engineers change the product continuously. When a change alters behavior that a help page describes, the page becomes inaccurate, and nothing in the release process alerts the documentation team.</dd></div>
  <div><dt>Who uses it</dt><dd>The documentation team.</dd></div>
  <div><dt>What it does</dt><dd>Each run reads the most recent completed code changes, confirms which of them customers can actually reach, and uses Claude to assess each change against an index of every documentation page. The output is a dated report of pages likely to need revision.</dd></div>
  <div><dt>My part</dt><dd>I designed and built it.</dd></div>
</dl>

## How it works

<ol className="ia-steps ia-steps--4" aria-label="How the evaluator works">
  <li>Read recent code changes</li>

  <li>Publish a dated report</li>
</ol>

## What made it work

<HubGroup columns={2}>
  <HubCard icon="git" tag="Lesson" title="Watch where new work appears first">
    An early version watched the copy of the code reserved for testing and caught only one of the nine changes in a release. New features reach the main development code first, so that is where the evaluator now looks.
  </HubCard>
  <HubCard icon="search" tag="Lesson" title="Finished code may not be released yet">
    A change can be complete well before customers see it. The evaluator searches for distinctive text from each change in the pre-release version of the product, so the documentation tracks what customers can actually use.
  </HubCard>
</HubGroup>
