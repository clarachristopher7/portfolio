# PR-to-docs impact evaluator

Answers one question: what shipped in the product that the docs have not caught up with. It runs as a scheduled CI job and writes a Markdown report as an artifact. It files nothing and changes nothing: a person reads the report and decides.

<p className="case-label">Two details that decided whether it worked</p>

- **The branch it scans.** Most feature branches merge into `dev` and only reach a release through a roll-up. Scanning `qa-stable` instead caught 1 of 9 merges for the August 2026 release: the job was technically running and almost entirely blind.
- **Merged is not shipped.** Walking merges between the two newest `r20*` tags tells you what landed in the repository. Fingerprinting each diff and searching the served preview bundle tells you what a customer can actually reach, which is the thing documentation has to match.

Claude is called once per merge, with the index of every docsite page as a cached prefix and only the merge subject plus a trimmed diff varying per call, so the expensive context is paid for once and reused across the batch.

<p className="case-label case-label--close">What this demonstrates</p>

Treating documentation drift as a measurable condition of the codebase rather than something noticed in review, and keeping the automation strictly advisory, so it reports and a person decides.
