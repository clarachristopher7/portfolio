# Documentation impact evaluator

<p className="hub-sub">A scheduled job that compares recent code changes with the docs and flags the pages those changes probably made wrong. It only reports. A writer decides what to change.</p>

<dl className="ctx">
  <div><dt>The situation</dt><dd>Engineers ship changes to the product all the time. When one of them changes behavior that a help page describes, that page is now wrong, and nothing in the release process tells the docs team.</dd></div>
  <div><dt>Who uses it</dt><dd>The docs team.</dd></div>
  <div><dt>What it does</dt><dd>On each run, it reads the latest code changes, checks which ones customers can actually use yet, and has Claude compare each change against an index of every docs page. You get a dated report of the pages that likely need an update.</dd></div>
  <div><dt>My part</dt><dd>I designed and built it.</dd></div>
</dl>

## How it works

<ol className="ia-steps ia-steps--4" aria-label="How the evaluator works">
  <li>Read recent code changes</li>
  <li className="is-new">Check what’s actually released<small>Key step</small></li>
  <li>Compare each change with the docs</li>
  <li>Publish a dated report</li>
</ol>

## What made it work

<HubGroup columns={2}>
  <HubCard icon="git" tag="Lesson" title="Watch where new work shows up first">
    My first version watched the copy of the code used for testing, and it caught one of the nine changes in a release. New features land in the main development code first, so that’s where it looks now.
  </HubCard>
  <HubCard icon="search" tag="Lesson" title="Finished doesn’t mean released">
    A change can be done long before customers see it. So the evaluator looks for distinctive text from each change in the pre-release version of the product, which keeps the docs in step with what customers can actually use.
  </HubCard>
</HubGroup>
