# PR-to-docs impact evaluator

A scheduled CI job that compares what has shipped in the product against what the documentation covers, then writes a Markdown report listing the pages that look out of date. The report is saved as a build artifact. The job does not open tickets or edit any pages. Someone reads the report and decides what to do with it.

<p className="case-label">Two details that decided whether it worked</p>

- **Which branch it reads.** Feature work lands on `dev` first, and only reaches a release later when `dev` is merged in as a batch. An early version of the job read `qa-stable` instead, and found 1 of the 9 changes that went into the August 2026 release. It ran and reported every day while missing almost everything.
- **Merged code is not always live code.** Reading the merges between the two most recent release tags shows what went into the repository. To find out what customers can actually reach, the job takes a distinctive piece of text from each change and searches for it in the JavaScript the preview site is currently serving. Documentation has to match what is live, not what is merged.

Each change gets its own call to Claude. The list of every page on the docs site is the long part of the prompt, so it sits in the same position on every call and is served from cache after the first one. Only the merge title and a trimmed diff change between calls, which means the long part is paid for in full once rather than on every call.

<p className="case-label case-label--close">What this demonstrates</p>

Treating documentation drift as a measurable condition of the codebase rather than something noticed in review, and keeping the automation strictly advisory, so it reports and a person decides.
