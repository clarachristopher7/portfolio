# Information architecture for a product estate

Documentation for a multi-product security portfolio had grown up per product, in incompatible source systems, with no shared definition of what a complete doc set looks like. I built an instrument that puts the whole estate on one axis, shipped as a single self-contained HTML file with no build step and no dependencies, so any stakeholder can open it and any writer can maintain it by editing one data object.

## In brief

**Problem.** Documentation for a multi-product security portfolio had grown up per product, in
incompatible source systems, with no shared definition of what a complete doc set looks like. Nothing
let anyone compare two products on the same axis, so gaps were argued rather than shown.

**Constraint.** It had to be openable by any stakeholder and maintainable by any writer: a single
self-contained HTML file, no build step, no dependencies, edited through one data object.

**What I tried.** [What you considered and rejected. A spreadsheet or a BI dashboard is the obvious
first answer for an estate survey, if you ruled those out, say why. Likewise any earlier scoring scheme
that turned out to be unmaintainable or too subjective to defend.]

**What I shipped.** An instrument that puts the whole estate on one axis: three views of the same data,
statuses decided by rule rather than opinion, an Evidence column naming what each status was read from,
counts derived from navigation data files rather than estimated, and a floor of guarantees every product
gets regardless of negotiation.

**What changed.** [See the Outcome section below, decisions unblocked, products surveyed, adoption by
other doc owners.]

Five archetypes exist, and each one is a claim about who the reader is and what they are trying to finish. That claim is what decides both the applicable sections and the journey stages:

| Archetype | Why it is its own shape |
|---|---|
| Cloud service, self-serve activation | Activation metrics apply directly: tenant activation, time to first value, seats in production. |
| Appliance and firmware | Bought through a partner, deployed once, run for years. Activation is registration and licensing; scale is HA and central management. |
| End-user client guide | The reader is an employee, not an administrator. There is no activation or scale journey; the metric is support deflection. |
| Partner and MSP console | The reader manages other organisations. The journey is tenancy and delegation, not product features. |
| Shared cross-product content | Not a product. Holds the pages that belong to no single product because they describe two things meeting. Canonical once, cross-referenced from every product that touches them. |

The five rules a solution guide has to meet:

- **Orchestrate, never duplicate.** Steps link to the canonical task pages. Today 101 links point into the docs, but 62 of those go to intro and quickstart and only around 22 into the configure sections, so settings are being restated inside guides instead of linked, and will drift.
- **State the deployment model and prerequisites up front**, so an evaluator can self-select rather than reading to the bottom to find out the guide was not for them.
- **End with a next step into production scale or operate**, or the guide dead-ends at a demo.
- **Require at least one tag.** Seven of 26 are untagged and therefore invisible in the filtered catalogue they exist to populate.
- **Cross-link both ways:** a Related solutions block on the feature page, so operators find the scenario too, not just evaluators.

**Release notes** span Operate and Expand, and carry one rule: link into the pages that changed, so a reader lands on current instructions rather than a changelog line.

## What every product gets regardless

Part of the model is a floor, provided once rather than negotiated per product: one search index across every product, a version selector per product, a last-updated date on every page, old URLs preserved as page aliases, a PDF download where one exists, one centrally owned theme, and a content lint gate on every merge.

Five decisions recur for every product as it moves onto the platform: which existing targets or guides still publish, the condition policy per target, whether PDFs are kept, generated from source or retired, whether the glossary and index are dropped or rebuilt, and which URL aliases carry over from the currently published site.

## How a status is decided

Statuses follow a rule, not an opinion. **Have** means a dedicated top-level nav section exists. **Partial** means pages exist but sit scattered under other sections, or number fewer than five. **Missing** means nothing matches. **n/a** means deliberately out of scope for that doc set. Every status carries an Evidence column naming what it was read from, and counts are derived from navigation data files and converted tables of contents rather than estimated, so any number in the map can be regenerated rather than defended.

Where a gap is claimed, the evidence is a case count: version-gated limits living in forum replies rather than a compatibility matrix, an end-user guide where 0 of 86 pages match any troubleshooting pattern, a cross-portal activation path worth 397 cases in one product alone.
